# Portable foundation contract vectors

These UTF-8 JSON files describe existing foundation contracts. They can be
loaded directly from `docs/contracts/` in the source distribution (sdist),
without importing Python. The wheel contains library code; it does not contain
these documentation fixtures. Use the sdist from the same release as the
library when checking another-language implementation.

| File | Vector format | Existing contract checked |
| --- | --- | --- |
| `ingestion-content-vectors.json` | `techflex-ingestion-content-vectors/1` | Manifest canonical bytes and SHA-256, upload slot mapping, receipt bytes and retirement, complete rejection inputs |
| `error-envelope-vectors.json` | `techflex-error-envelope-vectors/1` | `ErrorEnvelope.to_document()` and invalid constructor inputs |
| `payload-schema-vectors.json` | `techflex-payload-schema-vectors/1` | Per registered payload schema: segment metadata, manifest, and segment, manifest, set and product rejections |
| `license-document-vectors.json` | `techflex-license-document-vectors/1` | `LicenseDocument` canonical bytes and public Ed25519 verification |

`vector_schema` identifies each fixture format; it is not a new wire field or
a JSON Schema document. Package release versions, vector-format versions,
manifest format/schema/codec integers, license `format_version=1`,
`entry-parts/1` and receipt `content/1` are independent versions. This addition
does not change any of those contracts or the previously published positive
manifest/receipt canonical bytes. Consumers should dispatch on a recognized
`vector_schema` and refuse an unknown fixture version.

## Execute the inputs

Expected values are frozen in the files, rather than generated by the library
under test. `tests/test_portable_contract_vectors.py` executes the complete
negative ingestion inputs and the error/license vectors through public APIs.
`tests/test_ingestion_content.py` executes the existing positive manifest and
receipt vectors against the real ingestion service.

For ingestion, `manifest` is the complete manifest document. `slots` contains
upload inputs in global index order, including payload hex, byte size and
SHA-256. Decode hex into bytes before hashing or uploading. Entry and local
indices describe the manifest mapping; do not use them to reorder uploads.
Each negative case supplies its own full manifest and slots: upload those
bytes into a fresh session, then complete with that manifest. `content-conflict`
means `IngestionConflict`; `malformed` means `IngestionMalformed`. Neither
outcome may create a receipt or publish a manifest object. Receipt examples
preserve historical missing-version bytes and reject local retirement for
unknown verification versions.

For errors, construct the existing envelope from `input`; compare its
`to_document()` result with `expected_document`, or reject the input with
`expected_error`. `ManifestMalformed` is the existing empty-text validation
exception; it is not a new gateway error code. The five wire fields are
`code`, `message`, `correlation_id`, `retryable`, and `action`. Example action
names are fixture vocabulary, not foundation business actions. An unknown
action remains a valid envelope; consumers follow the existing `retryable`
fallback rule documented on `ErrorEnvelope`. There is no envelope version
field or new HTTP status mapping.

For licenses, `signed.document` is the format-1 payload, `canonical_hex` is
the exact signed UTF-8 byte representation, and `sha256` hashes those bytes.
UUIDs are strings, absent optional claims are null, features are sorted, and
timestamps retain the documented ISO offset spelling. Canonical JSON uses
sorted keys and compact separators. The vectors deliberately use ASCII values;
they do not introduce a general JSON canonicalization standard. Signature
text is base64; `public_keys_hex` contains raw 32-byte Ed25519 public keys.
Pass the supplied keyset, signature metadata and document to the existing
`LicenseKeyset.verify()` contract. The tampered document has its own correct
canonical bytes and hash but retains the original signature, so verification
fails. Unknown and revoked keys fail key resolution. The fixtures contain
only public keys and signatures, never signing private keys. This foundation
format is not an application's differently versioned license DTO.

## Payload schema vectors

`payload-schema-vectors.json` has one entry per schema registered by
`default_payload_schema_registry()`: `raw-segment/1` (`frame-segment`),
`insole-session-archive/1` and `gait-session-archive/1` (`byte-segment`). Each entry carries `segments` (metadata, base64 payload and
canonical bytes), one `manifest` (document, canonical bytes, SHA-256) and
rejection cases. `segment_rejections` and `manifest_rejections` give complete
documents that must be refused; `set_rejections` describe manifests that
differ from, or omit, received segments; `product_rejections` name a product
the schema is not registered for. The `segment` block of `raw-segment/1` is
the existing feet-force-plate vector (`canonical_hex`, `metadata_header`,
`payload_base64`, `sha256`) frozen byte for byte; the second segment and the
manifest are added. Canonical JSON uses sorted keys and compact separators.
The `insole-session-archive/1` segments and manifest are the RAY-825 vectors
frozen byte for byte from feet-force-plate (its manifest requires `ended_at`
and `local_quality_outcome`; the service completes only `VALID`, a rule of the
service rather than of this registry). `gait-session-archive/1` is split by
byte `offset` (optional, and contiguous when stated); its manifest
`gait-session-manifest/1` carries `codec`, `archive_sha256`, `archive_size`
(equal to `total_bytes`) and `part_size`, with `ended_at` optional and
`local_quality_outcome` optional and defaulting to `UNKNOWN` without a
completion gate. Frame, clock, compression and cipher fields are refused on
both. Schemas that applications register later publish their own entries here.
Validation is strict about types: integers are not coerced from text or floats. `raw-segment/1` keeps the existing service's rule that a manifest may omit `schema_version`. The registry adds no HTTP route or database, and a vector proves the
contract, not a deployed service.

## Session-create vectors

`session-create-vectors.json` (`techflex-session-create-vectors/1`) publishes
the product-neutral session core and one entry per schema. The `core` block
lists the fields every product sends: `session_id`, `client_installation_id`,
`started_at`, `versions.app` and `versions.payload_schema` are required;
`site_id` is required but may be `null` (the tenant comes from the terminal
credential, never from the document); `config_snapshot` is an optional JSON
object. `versions.payload_schema` selects the registered schema, and that schema
declares any further `session_extension` fields, `version_extension` keys inside
`versions` and equalities between fields. Anything a schema does not declare, or
a declared required field that is missing, is refused.

| Schema | Extension the schema needs |
| --- | --- |
| `raw-segment/1` (feet-force-plate) | `subject_uuid`, `consent_record_id`, `device_id`, `terminal_id` (must equal `client_installation_id`), `test_protocol{id,version}`, and `versions.calibration`, `versions.protocol_profile` — the existing `SessionCreateRequest`, unchanged |
| `insole-session-archive/1` | none: core fields only |
| `gait-session-archive/1` (gait-IMU) | none: core fields only |

Each entry has a `session` (document, canonical bytes, SHA-256) and
`session_rejections`: complete documents that must be refused, including every
feet-force-plate-only field sent to a schema that does not declare it. The
insole and gait-IMU entries are core-only registrations (RAY-833); a later
field such as a subject reference or device serial is a separate requirement
revision. `local_quality_outcome` is
a manifest-level field and is not part of the session.

## Application boundary

These fixtures prove portable library contracts, not deployed HTTP behavior.
Business access/subjects/consents/session/status routes, HTTP OpenAPI,
product-specific error mappings, endpoint idempotency DTOs and native-client
integration belong to the application delivery. No successful execution here
proves that a business service has registered a product, been deployed, or
passed another-language tests.
